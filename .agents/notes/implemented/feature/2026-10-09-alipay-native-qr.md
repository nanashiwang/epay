# Agent Note: 支付宝原生收款码与账单确认

Status: implemented

## Problem

同一企业账号在原生支付宝收款码入口可收款，而现有 alipaycode 的 UID 转账入口被支付宝中断。账务查询成功不代表付款入口已通过验收。用户要求使用自己的原生收款码；新入口必须能处理不含订单备注的真实收入流水，并避免同金额、重复流水造成重复入账。

## Existing capabilities and impact

- `plugins/alipaycode/alipaycode_plugin.php` 已包含网页/API 提交、二维码和付款入口，配置支持普通转账和转账确认单。
- `plugins/alipaycode/server.php` 查询已验签账务流水，原先仅匹配备注与金额，然后复用 `processNotify`。`getshop.php` 读取服务端订单结果。
- 扩展原插件的支付类型和 `appurl` 配置，不新增支付产品或数据库表；旧两种入口保持兼容。原生码使用独立收银台以清楚呈现金额、过期状态和手机打开入口。
- 搜索活跃笔记未发现支付宝功能归属笔记；现有能力审查流程笔记与本决定无功能重叠。

## Decision

增加原生收款码类型，限定 HTTPS 的 qr.alipay.com 码地址，二维码直接编码该地址，不嵌套 UID 转账或未经文档确认的金额参数。付款人按页面金额付款。

账单确认优先使用完整订单备注；无备注时，只匹配相同收款账号、相同分金额、创建后五分钟内的唯一订单。候选集包括已支付订单，存在歧义拒绝自动确认。只接受收入和有效支付宝流水号；在数据库锁内重新检查订单与流水重复使用，再调用现有回调。保留三分钟到账查询宽限，以交易发生时间判断是否在付款窗口内。

网页/API/直接付款路由共用相同原生码页面，过期与已付款不再显示可支付二维码，成功始终由服务端订单状态决定。

## Alternatives considered

- 保留 UID 转账最省改动，但不能满足用户复现原生收款码入口的要求，且不能假定换域名就能通过风控。
- 强制备注可准确关联订单，但已观察的原生码流水没有备注，无法覆盖此收款流程。
- 随机调整应付金额可以提高并发可用性，但改变客户实际付款和费用语义，当前选择冲突时不自动认领，不加入隐式加价。
- 无条件按金额认领实现简单，但同额订单、迟到付款和重复扫描会误入账，故拒绝。

## Verification

- PHP 8.3 语法检查和 80 项隔离测试通过，覆盖匹配、冲突、重复、锁释放、三个付款入口、页面状态和付款人身份检查边界。新增 CI 运行同一测试。
- 浏览器验证桌面和窄屏布局、深色样式测试夹具、查询失败和服务端确认后的返回；极窄屏二维码溢出已修复。
- 用户收款图片的解码值与其已有成功收款通道配置一致。实际付款及业务回调仍是部署后的独立验收，不计入隔离测试结论。
- 生产使用原生 PHP/MySQL，有既有个性化修改，因此只发布本插件变更；不整体拉取或运行 Docker 更新脚本。验收前通道保持关闭。

## Consequences

静态收款码不能锁定金额、撤销过期扫码或证明某笔无备注收入来自本网站。跨平台同时使用同码，以及站外同额转账，无法仅凭账务查询消除歧义；无备注匹配适合专用收款账号、低并发业务。必须保留金额冲突、超时与漏单的人工核对流程，不将一次成功视为风控保证。未做真实付款前不能宣称端到端可用。
