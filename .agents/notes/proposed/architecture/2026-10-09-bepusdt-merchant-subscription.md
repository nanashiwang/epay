# Agent Note: 商户包月订阅与 BEpusdt 自助接入

Status: proposed

## Problem

用户已明确业务模式：商户按月付费使用 Epay，并自行配置收款网关。需要把 BEpusdt 纳入可追踪上游，提供商户自己的加密货币收款入口。平台订阅收入、商户直收本金和支付成功依据必须各有明确归属。

本轮完成上游登记、代码与接口审计及融合设计；没有实现本提案的订阅权限或 BEpusdt 自助配置，没有部署、迁移或真实链上付款。本提案不代表已上线能力。

## Existing capabilities and note audit

- `plugins/bepusdt/bepusdt_plugin.php` 已有创建交易、跳转网关收银台、签名回调和 return 页面。入口复用 `submit.php`、`submit2.php`、API 路由、`Channel` 与 `Payment::processOrder`。
- `user/groupbuy.php`、`user/ajax2.php` 的 groupbuy 和 `pre_group` 已提供售价、月数、购买/续期；`pre_user.gid/endtime` 保存会员资格。`tid=4` 支付订单和 `reg_pay_uid` 已分离购买人和平台收款商户。
- 现有续费在下单时算出 endtime，回调直接覆盖；并发续费、迟付及月末算法需补契约。`cron.php` 定时降级不是即时的订单准入检查。
- `pre_subchannel.uid` 可承载商户账号身份，`mode=1` 已走直清。本地费率 `100` 通常表示零比例服务费，但最低手续费仍可额外收费，不能只改 rate 就声称纯包月零抽成。
- 工作区已有支付宝自助收款未提交实现：`user/collection.php`、`CollectionAccount`、加密配置、流水和通知审计。当前保存/路由/健康逻辑硬编码支付宝，`pre_collection_route` 以 uid 为唯一键，尚不是通用多网关能力；不能直接套入加密货币字段。
- 活跃笔记审计：工作区的 `.agents/notes/proposed/feature/2026-10-09-merchant-collection.md` 部分重叠，作为账号/UI/通知复用边界；该笔记尚未提交，不作为本提案发布依赖，本轮不改动其所有者笔记或代码。[原生码匹配](../../implemented/feature/2026-10-09-alipay-native-qr.md) 保留支付宝匹配规则，不扩展为链上规则；[能力核对流程](../../implemented/process/2026-09-29-capability-review-and-decision-notes.md) 是协作规范，无需替代。
- 可重复审计命令、准确上游提交和正式版信息见 [UPSTREAMS](../../../../docs/UPSTREAMS.md)。

## Proposal

### 1. 收费与资金归属

首期采用固定周期预付订阅：复用会员购买入口，升级展示为“我的套餐”，提供购买、续期、到期时间、权限/用量、付款与变更记录。价格、账号限额、支付方式白名单均由管理员配置，本提案不代定售价。

- 商户向平台支付月费 → 平台自有收款通道确认 → 开通该商户套餐。
- 客户向商户付款 → 商户自己的 BEpusdt 确认 → Epay 记录订单并通知商户业务站 → 币进入商户自己的钱包。
- 套餐权益建议包含允许的网关/网络、可启用账号数及必要的订单速率上限，首期不引入复杂阶梯计费。主推纯包月套餐的订单服务费为零，明确覆盖最低手续费、成本/利润和邀请返利，不能影响其它旧套餐。
- 商户自带网关仅用于商户业务订单和受限测试订单；平台会员费、平台余额充值、保证金及其它增加平台权益的订单只能使用平台信任的收款通道。商户掌握自己的 Token，能自行构造有效签名，不能用其回调作为平台已收到月费的依据。
- 商户直收本金不加入 Epay 可提现/待结算余额。财务页区分平台月费、商户交易额与链上币额。

### 2. 配置与接入体验

首期采用商户自带 BEpusdt 实例（BYO）：Epay 的“收款账号”增加 BEpusdt 类型，表单包含账号名称、HTTPS 网关地址、API Token、允许的币种/网络、可选的指定收款地址。超时及汇率覆盖放在高级设置。

先保存 → 测试接口 → 创建待支付测试单 → 确认真正付款、金额与回调 → 启用。各状态分别显示；接口可达或保存成功不能标为已验收收款。测试付款由商户主动发起，不自动转账。

沿用 Epay 当前法币订单口径，首期固定 CNY，币种/网络由管理员白名单和商户选择共同限制；建议先开放 `usdt.trc20`，其它网络通过独立验收后开放。不能仅添加 USD 下拉框，却仍把金额记为人民币。

复用账号所有权、CSRF、密钥加密和通知审计机制，提取小范围 provider 适配接口，分别处理支付宝轮询和 BEpusdt 回调。公共账号元数据与网关特有配置分开；子通道身份保留。默认路由必须至少按 `(uid, payment_type)` 区分，不让 BEpusdt 覆盖支付宝默认账号。

网关 URL 由用户输入，必须开启 TLS 主机/证书验证，限制协议/端口/重定向，校验 DNS 和实际连接地址，阻止访问回环、内网、链路本地及云元数据地址，包含 IPv6 和 DNS 重绑定情形。受控私网部署须由管理员单独允许。返回的 payment_url 也需限制为已配置网关来源。Token 不回显，不写普通日志；不索取钱包私钥、助记词。

账号状态展示“配置校验、最近回调、待处理订单、失败通知”，不复用支付宝的两分钟轮询心跳判定。可启用账号数按有效套餐校验；降级超限时要求选择保留账号，禁止随机换收款方。

### 3. 订阅准入与续期

复用现有 group 作为套餐目录和 uid/gid/endtime 身份，增加统一订阅权限服务及付款/权益变更流水；不建立第二份独立会员到期时间来源。

Web/API 下单、收银台重新创建交易、账号启用、默认路由及通道枚举必须走同一权限判断，同时保留商户审核等原有限制。过期/停用只阻止新交易；已建立交易仍按订单保存的账号、配置版本及付款窗口处理确认和通知，不能因商户过期而丢失到账。只读订单/账单、续费和停用操作仍可用，失败不回退到平台或其他商户收款。

同套餐续费在实际支付成功事务内锁定商户，按 `max(当前有效期, 支付生效时间)` 增加购买周期；每个付款订单只能生效一次。记录套餐和价格/周期快照、支付订单、原/新到期时间及操作者，不能使用下单时的旧 endtime 覆盖较新的续费结果。沿用自然月语义并明确月末钳制，例如 1 月 31 日续一个月至 2 月末；定义时区与到期时刻，测试月末、闰年及并发续费。

套餐切换首期不做自动折算：普通商户在线仅续购同套餐，变更套餐由管理员明确指定生效时间并留审计。页面展示真实已支付结果，不能依据 `?ok=1` 显示购买成功。充值余额购买和外部支付共用权益事务和幂等约束。

这里的“包月”是按月购买/续期；BEpusdt 转账收款本身没有经用户授权的周期自动扣款能力。提醒续费和真正自动扣款是后续独立能力。

### 4. 创建、到账与数据契约

复用 `create-transaction` 和网关收银台，首期不做自建链上扫描器或多链收银台。Epay 继续向商户业务站提供原来的支付与通知协议。

- 保存本次交易的 Epay 订单、商户/账号、网关实例、配置版本、上游 trade_id、法币/网络、地址、应付币额、汇率依据和过期时间。金额以定点精度处理；按锁定版本的 JSON 数值要求编码和签名，覆盖 `1`/`1.00` 等格式差异。
- 强制正额普通订单，禁止零金额触发任意金额到账模式。币额使用网关实际返回值，因为同地址同金额冲突时网关可能微调币额；页面提示必须按所选网络及显示金额付款。
- 相同 order_id 的再次创建会重建交易并重置超时，不能将其视为无副作用重试。保存并复用既有支付链接，创建过程串行化；请求结果未知时进入待核对，不盲目重建或换钱包。
- 严格解析回调结构，使用固定格式签名和常量时间比较；成功条件包含绑定的订单/trade_id、法币金额、收款地址、币额及状态。网络/法币来自不可变创建记录，不能假设回调含这些字段；`buyer` 当前缺失，按可选字段处理。
- 固定金额首期只接受约定币额；网关若启用容差匹配，多付/少付进入核对流程，不静默视为正常。状态 1/3 只更新等待/超时记录，不能给已付订单降级；状态 2 的重复/并发通知只结算一次。
- `block_transaction_id` 用于链上证据关联，但去重不能简单全局按交易哈希：多网络、同交易多转账事件需要网络与事件/接收地址维度；上游缺事件 ID 的歧义进入人工核对。
- 提交数据库事务后才确认上游通知成功，下游业务通知单独重试。配置变更、停用、归档和 Token 轮换必须保留在途订单处理所需的版本；不直接改已有订单的钱包或签名密钥。
- 回调缺失通过独立对账恢复。本次看到 `/api/v1/pay/info` 是面向收银台的查询且有指纹约束，不承诺它可直接作服务端可信查单；实施时核实所选版本的查询能力，必要时由网关提供受认证的服务端查询，不以浏览器跳转或普通查询页直接认定付款。
- 首期不提供自动链上退款；保留异常和人工处理记录，不把账面退款当作链上转账已完成。

### 5. 上游与部署边界

BEpusdt 作为独立服务运行，拥有自己的数据库/持久化目录、钱包配置和版本；Epay 保持当前 PHP/MySQL 和部署脚本。上游跟踪与 Epay 主线、发布标签隔离。先做协议契约适配，再按版本部署，不直接把 Go 网关代码合入 PHP 项目。

若以后提供平台托管模式：商户可只填钱包地址，Epay 持有网关 Token，并负责服务器侧商户身份、钱包归属、订单隔离和限流；必须核验指定地址能否被网关接纳及监测。可选择每商户隔离实例或受控共享实例，但在隔离设计验收前不开放。当前实例级 Token 不能下发给全部商户。

## Alternatives considered

- **仅启用已有 BEpusdt 插件**：最快能由管理员配置收款，但没有商户自助、套餐权限、凭据保护和完善回调核验，无法覆盖本次商业模式。
- **商户自带网关（首期推荐）**：隔离边界清晰，能复用现有插件；代价是商户需自行部署和维护网关，平台只能保证自己的接入部分。
- **平台托管网关**：商户只填钱包，使用门槛更低，适合后续增值套餐；代价是平台承担扫链、节点、容量和多租户隔离，需要先实现服务端代理，不直接共享 Token。
- **新建整套订阅及支付系统**：可自由设计，但会重复现有 groupbuy、订单状态、账务与通知，增加双重事实来源；选择扩展现有能力并补关键事务。
- **用网关原生易支付接口完全替代本项目收款入口**：兼容简单调用，但商户套餐、账号权限和统一审计仍要由 Epay 管理，因此保留 Epay 作为业务入口。

## Acceptance criteria

1. 完成并验收现有商户账号工作后，抽取有限公共部分，覆盖原支付宝流程回归；不用本提案提交带入现有未提交代码。
2. 套餐入口与服务端权限一致；验证并发购买/续费、月底、迟付、伪造前端成功参数、过期及降级限额，平台权益拒绝商户网关回调。
3. 验证账号归属、Token 加密/轮换、URL/重定向/DNS 限制、插件创建的金额编码与响应核验；等待/超时/成功/错误金额/重放/乱序/跨账号回调均有契约测试。
4. 实际数据库验证直收本金不入余额、纯包月无比例或最低手续费、通知重试和异常事务可恢复；日志保留金额、时间、订单号与链上证据且不泄密。
5. 浏览器验证普通商户的购买续期、新增配置、状态反馈、支付结果、到期页面、刷新、窄屏和失败情况；平台管理员与其它商户不能误用配置。
6. 最后在单个经允许的网络进行真实小额付款，核对钱包到账、Epay 订单、独立业务站通知及原额/币额记录。模拟通过、接口连通、CI 成功均不代表生产收款已验收。

## Risks

当前支付宝自助账号改动尚未提交，通用化必须在归属清晰的基础上推进。上游文档、main 与发行版可能不一致，必须锁定版本测试。商户掌握网关会扩大回调信任边界，只能影响其自有业务订单；平台订阅通道须隔离。静态钱包地址跨业务复用、金额微调、迟付及确认延迟会产生对账例外，需要专用收款地址、清晰付款页和可追溯处理。
